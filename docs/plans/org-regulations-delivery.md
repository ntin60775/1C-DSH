# Спека: поставка орг-регламентов

> План-гейт (20.11): спека утверждена оператором без правок; три раунда
> фронтира grilling, решения принял оператор.
> Гейт проекций (20.11): четыре среза critic, 27 находок подтверждены
> (T1–T27, отчёт tickets/org-regulations-delivery/critic-triage.md);
> спорная T8 решена оператором (архив+замена copy без ask); правки по
> всем находкам утверждены оператором. Состав «Готово» и «Ограничения»
> читается с правками гейта проекций.

## Цель

Базовые регламенты разработки организации живут в локальных репо контор
и поставляются в проекты парка как паки стандартов OntoShip (`type:
team`). Привязка семантическая: класс = «пак команды» проекта, имена
репо нигде не зашиты. Обновление централизованное и тихое: вопросы
одноразовые на настройке и по аномалиям. Фриланс-сценарий закрыт: N
контор на одной машине, на разных ПК разные конторы. 1C-DSH работает
без паков структурно (`src/` не содержит `.agents`).

Термины: контора = команда (организация) = org; team-пак = пак команды
= регламент-пак (`type: team` контракта пака).

## Решения

Принял оператор 20.11: обсуждение привязки и фриланс-модели, три раунда
фронтира grilling, гейт проекций (T8).

| # | Решение |
|---|---|
| 1 | Привязка семантическая: класс = team-пак проекта (`type: team`); имя репо и пака свободное, несёт идентичность конторы; один проект — один team-пак своей конторы. |
| 2 | Протокол поставки/обновления пака на один проект — новый скилл `pack-deploy` в репо contour-deploy; `1c-contour-deploy` зовёт его шагом исполнителя; deliver не расширяется (скоп — ядро). |
| 3 | Привязка проект→контора — поле `org` в реестре парка (машино-локально); на новом ПК один батч-вопрос на парк, дальше молча. Git проекта и init не трогаем. |
| 4 | Доказательства — репетиция в /tmp + `--dry-run`; реальный парк только отдельной командой оператора после приёмки. |
| 5 | Орг-репо локальный, remote нет и не будет никогда; пак опционален для контура и проектов; правки норм только централизованно. Закреплено в AGENTS.md орг-репо (коммит 5ba7381). |
| 6 | Тихая замена copy-копии пака при обновлении: архив старого снимка вне репо с инвентарём + чистая поставка, без ask. Copy — снимок канона; «copy differs» — штатный путь обновления copy-канала, не дефект локальной правки. Полномочие явное (T8 проекций). |

Тривиальные развилки разрешены агентом по фильтру раундов:

- Контора→чекаут — ключ `regulations` (карта org→путь) в существующем
  `~/.config/contour-deploy.json`. Org — произвольная метка конторы,
  ключ карты `regulations`; имя пака с меткой org не связано,
  соответствие ведёт оператор.
- Канал пака — батч-вопрос link/copy на свежей установке; обновление
  тем же каналом молча; на дев-машине с чекаутами контор рекомендован
  link (коммит в орг-репо = обновление всех linked-проектов, пина
  версии на проект нет — это и есть «всегда одинаковы»). Смесь канала
  pack-deploy ловит до вызова установщика (T4).
- Триггер замены copy — отказ установщика «copy differs» при попытке
  `--pack`; `--check` с источником не сверяет (T7). Полномочие —
  решение 6.
- Акт обновления — запись в реестр парка: имя пака, версия (`version`
  манифеста, оба канала), канал (link/copy, из ФС), дата; для link
  дополнительно коммит чекаута (`git rev-parse --short HEAD`,
  dirty-маркер). Теги орг-репо не требуются (T3).
- Два team-пака в проекте — именованный отказ pack-deploy, вопрос
  оператору (конфликт норм по контракту пака); носитель инварианта —
  протокол pack-deploy (T17).
- Спека живёт в 1C-DSH (проект метода); тикеты адресуют репо-цели
  (contour-deploy, орг-репо, 1C-DSH).

## Готово

1. Скилл `pack-deploy` в `contour-deploy/skills/`: протокол одного
   проекта — входы из промпта исполнителя (резолв org→источник —
   оркестратор, п. 2), сверка `type: team` источника, канал,
   `install.sh --pack`, замена copy по решению 6 (триггер —
   отказ «copy differs»), отказ при двух team-паках, детекция смеси
   канала до вызова установщика, акт для реестра парка (факты —
   исполнитель, запись — оркестратор, п. 2). Доставка скилла:
   SKILLS-массив `contour-deploy/scripts/install.sh` +
   `tests/test_install.py` + README contour-deploy (T6).
   Доказательство: линт frontmatter + репетиция п. 6.
2. Схема данных: ключ `regulations` в `contour-deploy.json`, поле `org`
   и акт пака в реестре парка. Парковый резолв и запись реестра — на
   оркестраторе до fan-out (исполнитель-субагент ask не поднимает,
   докладывает факт); триггер батча — отсутствие поля `org` у целей
   или ключа `regulations` для резолвленной конторы; пустой реестр =
   стоп (нет целей), не батч (T1). Путь реестра — через ключ `fleet`
   (`${DSH_1C_STATE_DIR:-~/.dsh/state/1c}/projects.json`), писатель —
   оркестратор последовательно под `projects.json.lock` (контракт
   замка — как у doctor); схема org/акт — правка канона
   `docs/dsh-install.md` (T2).
   Смена конторы проектом: поле `org` правит оператор + переустановка
   пака; автосверки нет (T15). Доказательство: репетиция п. 6.
3. Шаг исполнителя «паки регламентов» в `1c-contour-deploy`:
   `.agents/packs` добавляется в поверхность установки; паки в
   gitignore — приёмка шага = акт в реестр парка, без коммита и вне
   автоприёмки контур-слоя (T5). Промпт исполнителя несёт путь чекаута
   contour-deploy (T6). Строка невалидного пака в выводе core
   `--check` = аномалия пака → пак-шаг, не дефект ядра (T18).
   Документация ключа `regulations` — README contour-deploy +
   Предусловия оркестраторов (T27). Доказательство: текст + репетиция
   одного исполнителя-субагента на одном temp-проекте (холодный агент,
   только текст протокола, T11); полный fan-out — первый живой прогон
   командой оператора, вне приёмки (названо).
4. Носители орг-репо: AGENTS.md — правила мейнтейнера (remote никогда,
   правки только централизованно, имя несёт идентичность конторы,
   коммит после валидатора); README — проверка `--check` валидирует
   контракт (не дрейф), обновление через команду деплоя, без тегов
   (T16, T17). Доказательство: коммиты в орг-репо.
5. Инвариантный тест 1C-DSH `tests/unit`: лексический инвариант «`src/`
   не содержит литерала `.agents`» (ловит и `join('.agents','packs')`),
   скан всего `src/`, счётчик + известный файл (паттерн
   `tests/unit/no-legacy.spec.ts`); мутация — резолв пути, не литерал
   (T21). Доказательство: `pnpm test` зелёный, мутация краснит.
6. Репетиция в /tmp: два temp-орг-чекаута с валидными team-паками
   разных имён + четыре temp git-проекта; изоляция — temp-конфиг и
   temp-реестр через параметры протокола (промпт несёт пути),
   checksum живых конфигов/реестров до/после (T10). Сценарии:
   отсутствие `org` → один батч-вопрос на парк → запись → второй
   прогон молчит; отсутствие ключа `regulations`; новый ПК — висящий
   link → relink; установка link и copy; link-обновление коммитом
   (проект видит новый текст без действий) и WIP-правкой (мгновенное
   распространение, dirty-маркер); copy-differs → архив+снос+поставка
   без ask (решение 6); одноимённый relink (подмес конторы); аномалии
   без записей (мёртвый чекаут, невалидный пак, два team-пака, смесь
   канала); битый манифест → `--check` красный + run_gates exit 2;
   `--dry-run` — ноль записей; акт name/version/channel/date в
   temp-реестре; повторный полный прогон — тишина; один
   исполнитель-субагент на одном temp-проекте (холодный, только текст).
   Ожидание `--check` на pack-only проекте названо (красный по
   отсутствующим скиллам ядра — репетиционные проекты получают ядро).
   Доказательство: отчёт с точными выводами и кодами в папке тикетов
   юнита; расхождение = дефект; шаг «из головы» = дефект текста.

## Рамки

- Не входит: наполнение регламентов и проза правил — проза есть
  содержание стандартов (нормы), не правила репо (T24); роли паков
  (reviewer-чек-листы) — вне v1, орг-пак v1 несёт только стандарты
  (T25); `ontoship-deploy` (v1 — только 1С-парк); deliver, install.sh,
  init (канал `--pack`, валидатор и обнаружение паков уже готовы);
  вендоренные паки стиля и БСП (свой механизм).
- Переименование `org-dev-regulations` под идентичность конторы —
  позднее решение оператора; миграция = снос старого каталога пака +
  установка нового (аномалия pack-deploy «два team-пака»), поставку
  не блокирует (T23).
- Новый ПК: орг-чекаут кладёт на машину оператор (перенос/копия;
  remote нет никогда); деплой резолвит существующий чекаут или
  называет пробел (T26).
- Реальный парк — отдельная команда оператора после приёмки репетиции.

## Ограничения

- Канал молча не меняется: pack-deploy сверяет тип цели с каналом до
  вызова установщика (copy-режим установщика молча заменяет link на
  copy); замена copy — только через архив с инвентарём (решение 6).
- `src/` 1C-DSH не содержит литерала `.agents` — инвариант п. 5
  «Готово»; оркестратор contour-deploy читает паки легитимно (счёт
  team-паков, версия) — граница про 1C-DSH, не про оркестратор (T22).
- Орг-репо: remote не создавать, не пушить.
- Link — живой контент: незакоммиченная правка орг-репо мгновенно
  видна всем linked-проектам; правка через симлинк из проекта меняет
  орг-репо (write-through). Агент проекта пак не правит; митигация —
  правило орг-репо «коммит после валидатора» (T12).
- Зона поражения битого манифеста в HEAD link-канала: `--check`
  красный во всех linked-проектах, run_gates отказывает весь прогон
  (exit 2, гейты всех паков включая стековые); между поставками
  узнают при check/гейтах. Принято, пин/откат не делается (T13).
- Подмес конторы: при одноимённых паках установщик молча перетыкает
  link/заменяет copy; защита — резолв pack-deploy по полю `org`,
  рекомендованные разные имена паков контор, кейс в репетиции;
  ручной `--pack` мимо pack-deploy — обход защиты (T14).
- Обновление тихое; ask только по аномалиям (мёртвый чекаут, невалидный
  пак, два team-пака, смесь канала) и одноразовая настройка.
- Правки contour-deploy — коммиты в его репо; версия — скилл `release`
  того репо по команде оператора.
