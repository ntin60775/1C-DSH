# Ишью 58: границы execute-фрагмента 1c-db

> План-гейт: утверждена оператором 06.11 («утверждаю»). Фронтир ушёл
> оператору, ответа нет — решения приняты по рекомендациям (правило
> «ответа нет — идти по рекомендации, назвав это в отчёте»); утверждение
> покрывает их.

## Цель

Установить фактические границы BSL-фрагмента `execute_code` тулкита 1c-db
живой матрицей проб на двух средах, задокументировать границы в каноне
контура (скилл 1c-test-contour, докстринги onec_db), подготовить кандидат
апстрим-репорта. Закрывает требования P1/P2 ишью
[#58](https://github.com/ntin60775/1c-zcode/issues/58) — с поправкой:
причина из ишью противоречит исходникам поставки (факты ниже), поэтому
дока пишется по матрице проб, а не по гипотезе.

### Решения (по рекомендациям, оператор не отвечал на фронтир)

1. Дока — по проверенной матрице проб, не по наблюдениям владельца.
   Цена ~1 ч живого стенда; канон по непроверенной причине закрепил бы
   неверный механизм.
2. Пробы — из этой сессии из шелла: стенд project-bp поднять
   `start_1c_db.sh`, фрагменты вычислительные, без записей данных, стенд
   погасить тем же заходом. Контрольная матрица — демо erp-demo.
   Альтернатива (сессия project-bp, канон «живая база — сессия проекта»)
   растягивает юнит на два сеанса — не выбрана.
3. Носители доки — 1c-test-contour и докстринги onec_db. Релиз wheel —
   вне юнита (отдельным словом оператора). Дубля в 1c-db-data нет —
   это слой канала и анонимайзера, не синтаксиса фрагментов.
4. P2 — кандидат апстрим-репорта: правки epf/прокси запрещены (апстрим
   GPL), черновик с числовым протоколом; отправка — слово оператора.
   Pre-flight-валидатор BSL в onec_db отклонён: свой парсер, хрупкий,
   ложные срабатывания.

## Контекст

Факты (проверены 06.11):

- Путь исполнения: `onec_db.execute()` — тула `execute_code`
  (`1c-onec-db/src/onec_db/core.py:104`) — прокси
  (`onec_mcp_toolkit_proxy/mcp_handler.py`, `execute_code`: код проходит
  без содержательных преобразований — pydantic-валидация, опасные слова,
  strip по краям в `validate_execute_code_params` (`tools.py`)) — epf
  `ВыполнитьКод` — `Выполнить(Код)` (клон
  `~/home/dev/contrib/clones/1c-mcp-toolkit`, тег 1.10.0 ca14a98, модуль
  формы `Module.bsl`, строка 3969). Номер строки в ошибке из ишью —
  «Форма(3969)» — совпадает с этой строкой: фрагмент шёл через
  `Выполнить`.
- «Через ВычислитьВыражение» — снято: `ВычислитьВыражение` в тулките нет
  вовсе (grep по клону — ноль; в 1.9.0 `Выполнить(Код)` на строках
  3628/3745; клиентская ветка `ВыполнитьКодНаКлиенте` — тоже чистый
  `Выполнить`).
- Платдок против «циклы не поддерживаются»: Синтакс-помощник 8.3.27.1859,
  статья Выполнить (root_Exec): ограничения — веб-клиент, COM-соединение,
  мобильные iOS; операторных ограничений нет.
- Среды одинаковы: project-bp — платформа 8.3.27.1859
  (`v8project.local.yaml`, `tools.platform.path`), erp-demo — та же;
  режим совместимости `Version8_3_27` у обеих
  (`src/cf/Configuration.xml`). Гейт «старая платформа или режим
  совместимости» для СтрДублировать снят.
- «СтрДублировать вне песочницы» — снято: функции `СтрДублировать` нет
  во встроенном языке (проверено по Синтакс-помощнику 8.3.27.1859:
  точный поиск по глобальному контексту не находит; есть СтрДлина,
  СтрНайти, СтрШаблон и другие, повтор строки — нет). Красная проба
  владельца «Процедура или функция с указанным именем не определена» —
  корректное поведение платформы на вызов несуществующей функции, в
  любом контексте. Проба остаётся в матрице как ожидаемо-красный
  контроль диагностики, не граница execute.
- Глобальные функции работают живьём: СтрШаблон (8.3.6) — носитель
  числового протокола в `skills/1c-test-contour/SKILL.md`; контроль
  доступности функций входит в матрицу.
- Молчаливый −1 во вложенных Если компилированной семантикой `Выполнить`
  невозможен: фрагмент компилируется целиком или падает. Механика не
  установлена — решающий эксперимент в юните.
- Зазор P1 реален: границ синтаксиса фрагмента в скиллах нет;
  1c-test-contour документирует только границы канала-токенизации.
- Прецедент докстрингов onec_db: `create_object` уже несёт границу
  окружения Выполнить («Новый(Тип(...)) ломает установку реквизитов»).
- Наблюдения владельца (тело ишью + коммент от 05.11, поздний): 2 красных
  цикла (таб и пробелы), 1 красный СтрДублировать («не определена»),
  2 зелёных базовых; 18 начислений однострочными Если — стабильно −1
  во вложенности 3 уровня без ошибки; плоский тернарник ?(…) — 19/19.
  Условия тех проб (версия epf, канал) не зафиксированы — пробел.
- Регресс «работал в эпоху Мозена» статикой не виден: ядро исполнения
  (`ВыполнитьКод`) между 1.9.0 и 1.10.0 не менялось; версия epf прогона
  Мозена неизвестна (пробел).

## Готово

1. Матрица проб исполнена на тест-ИБ project-bp, контроль — на демо
   erp-demo; артефакт — вывод скрипта проб: число или текст ошибки по
   каждой пробе, две среды. Состав: владельческие пробы (цикл с табом,
   цикл с пробелами, СтрДублировать — ожидаемо-красный контроль: функции
   нет в языке; СтрДлина), дискриминаторы (многострочный Если со
   счётчиком в двух ступенях — тривиальные условия и условия с вызовом
   функции — синтетика на −1; однострочный Если; Для-цикл;
   СтрШаблон-контроль; заведомая синтаксическая ошибка — сверка номера
   строки epf с клоном), базовые пробы `Результат = число`. Механика
   каждого расхождения названа (текст ошибки + строка epf). Стенды
   погашены тем же заходом.
2. Канон: секция «Границы execute-фрагмента» в
   `skills/1c-test-contour/SKILL.md` рядом с существующими границами
   окружения Выполнить в «Канон юнита» — матрица проверенного; правила
   запрещают только классы, которые матрица показала падающими или
   молчащими, работающее не запрещается; правило счётчика против
   молчаливого частичного исполнения, связь с числовым протоколом;
   живой пример фрагмента в скилле (многострочный Если с
   ВызватьИсключением) сверяется с новыми правилами. Линт скиллов
   15/15, гигиена имён чиста.
3. Докстринги onec_db (`execute`, `create_object`, `delete_object`) несут
   границы из матрицы; тесты onec_db зелёные; правки в main, релиз
   wheel — вне юнита.
4. Кандидат апстрим-репорта при воспроизведённом отказе: черновик
   `tickets/execute-fragment-limits/upstream-report-draft.md` —
   минимальный reproduction, числовой оракул, версии (тулкит, платформа,
   режим совместимости), вердикт носителя; среды в черновике
   обезличены. Если матрица отказ не воспроизвела — репорт не заводится
   (наблюдение остаётся с пометкой «не проверено»). Отправка — вне
   юнита, слово оператора.
5. Вердикт о носителе проблемы записан в секции канона как граница
   применимости, без имён сред: «воспроизводится на обеих средах» либо
   «воспроизводится на одной из двух сред».

## Рамки

- Вне юнита: правки epf/прокси (апстрим GPL), pre-flight-валидатор BSL в
  onec_db, правки тестов project-bp (проектная работа, не контур), гейты
  хуков (вне ишью), релиз onec_db, отправка апстрим-репорта, закрытие
  ишью 58.
- Пробы без записей данных: вычислительные фрагменты, числовые оракулы;
  анонимайзер не отключается (канон).
- Сервисы на время работы: стенды поднимаются скриптом и гасятся тем же
  заходом.

## Ограничения

- Канон не пишется по причине из ишью (ВычислитьВыражение) — противоречие
  исходникам; механика отказов — только из матрицы.
- Если матрица не воспроизводит отказы владельца: пробел «условия проб
  05.11 неизвестны» остаётся границей применимости; секция канона
  формулируется по матрице, неподтверждённые наблюдения идут в канон
  без даты и автора, с пометкой «не проверено».
- Сред в матрице две (project-bp, erp-demo); на другие проекты канон
  переносится правилом «границы проверяй пробой», без генерализации
  сверх матрицы.
