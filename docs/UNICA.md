# Unica: установка, версии, скиллы и MCP

Контур 1С — мягкая зависимость Unica: без неё гейт исходников отрезает
единственный путь правки 1С. Бинарники ставятся один раз на машину, скиллы
Юники и MCP-запись `unica` поднимаются в сессии 1С-проекта. Два канала
одновременно не держать: имя MCP-сервера `unica` одно.

## Канал и версия

Конкретные версии бинарей живут в `unica.yaml` в корне контура — это
единственный носитель: код, доки и скиллы их не дублируют. Ключи: `tag`
(тег релиза, он же тег скиллов), `unica`, `bsl-analyzer`, `v8-runner`,
`min` (минимальное ядро контура). Состав установленной поставки —
`runtime-manifest.json` schema 2 в каталоге установки; `/1c-doctor`
сличает yaml ↔ манифест ↔ кэш артефактов, живую версию ядра из
handshake лаунчера и версию скиллов Юники (`SOURCE.json`): рассинхрон
называется кодом (`mcp.unica-version`, `skills.unica-version`), а не
молчит.

## Глобальная установка

| Что | Где |
|---|---|
| Бинарники (ядро, `bsl-analyzer`, `v8-runner`) | `~/.local/share/unica/runtimes/<имя>/<версия>--<sha256>/<платформа>/` |
| Манифест установки | `~/.local/share/unica/<версия>/runtime-manifest.json` |
| Bootstrap | `~/.local/share/unica/<версия>/bootstrap/bin/<платформа>/unica-bootstrap` |
| Лаунчер | `~/.local/bin/unica` |
| Скиллы | `~/.local/share/unica/skills` |
| Кэш артефактов | `UNICA_RUNTIME_CACHE_DIR`, по умолчанию контура — `~/.local/share/unica/runtimes` |

В манифесте три артефакта: `unica`, `bsl-analyzer`, `v8-runner`;
ожидаемые версии — ключи `unica.yaml`. `rlm-tools-bsl` в манифесте
нет — не требовать и не искать. Маркер завершённости артефакта —
`.ready.json` рядом с каталогом платформы; оборванная закачка оставляет
`.partial` в корне кэша.

Лаунчер берёт версию из `UNICA_GLOBAL_VERSION` или максимальную в
`runtimes/unica` через `sort -V`, корень — `UNICA_GLOBAL_ROOT`, и
экспортирует перед запуском ядра полный handoff: `UNICA_RUNTIME_CACHE_DIR`
и `UNICA_ARTIFACT_CACHE` (кэш артефактов; по нему ядро резолвит движки),
`UNICA_RUNTIME_MANIFEST` (манифест установки), `UNICA_PROVIDER_STATE_DIR`
(состояние провайдеров — `<корень>/provider-state`). Без этого handoff
первый `push`/`pull` отвечает `bundled_tool_missing`, а с манифестом ядро
требует хост-контекст: доставка подаёт `ZCODE_PROJECT_DIR` корня проекта
(cwd-канал в строгом режиме не фолбэк). Лаунчер ставит
`scripts/install_unica_runtime.py`. Проверка установки —
`unica --help` (первая строка `unica <версия из unica.yaml>`).
Грабли: `sort -V` ставит rc-суффикс выше финала той же версии
(`<версия>-rc.N` > `<версия>`) — после обновления каталоги прежних версий
удалять, иначе лаунчер останется на rc.

## Установка и обновление

Единый путь — `scripts/install_unica_runtime.py` (версии и тег читает из
`unica.yaml`):

```bash
python3 scripts/install_unica_runtime.py          # поставить/обновить
python3 scripts/install_unica_runtime.py --prune  # то же + снос прежних версий
# снос не трогает кэш артефактов, скиллы и provider-state
```

Скрипт собирает `runtime-manifest.json` упаковщиком апстрима
(`scripts/ci/package-unica-plugin.py` тега) из релизных core-ассетов и
lock-файла тега `plugins/unica/third-party/tools.lock.json`, сверяет версии
движков lock ↔ yaml (расхождение — ошибка), собирает `unica-bootstrap` из
исходников тега (`cargo build --release --locked -p unica-bootstrap`;
в релизные ассеты bootstrap не входит), ставит контурный лаунчер
`~/.local/bin/unica` и греет артефакты prefetch в контурный кэш.
Повторный прогон идемпотентен: готовый bootstrap той же версии и
докачанные артефакты не пересобираются и не перекачиваются.
Требования: git, cargo, сеть до github releases.

`UNICA_RUNTIME_CACHE_DIR` при прогреве обязателен: без него bootstrap
выбирает кэш по цепочке хостов (например `~/.codex/unica/runtimes`), и
контурный лаунчер артефакты не найдёт. Скрипт экспортирует его сам.

Скиллы Юники ставит `scripts/install_unica_skills.py` (тег — из
`unica.yaml`), проверка — `python3 scripts/install_unica_skills.py --check`.
Полная проверка установки — `/1c-doctor` и `scripts/unica_ping.py`.

## Скиллы Юники

Скиллы — собственность проекта, не профиля: они видны только в сессии
1С-проекта. Ставит их `scripts/install_unica_skills.py`: разреженный клон
тега, каталог `plugins/unica/skills`, атомарная подмена
`~/.local/share/unica/skills`. Рядом ставятся `LICENSE` и `SOURCE.json`
(версия, тег, коммит, число скиллов) — проверка установки:

```bash
python3 scripts/install_unica_skills.py --check
```

Прежняя установка скиллов не нужна: подмена каталога целиком, половины
скиллов не бывает. Источник — LGPL-3.0, текст лицензии едет с каталогом.

Провайдер скиллов доставки поднимается в области агента и видит три
корня: `skills/` контура, `commands/` контура и `~/.local/share/unica/skills`.
Вне 1С-проекта скиллов Юники в каталоге нет.

## MCP-запись `unica`

Запись ставит доставка контура (хост-плагин), а не проект. Stdio-команда записи — `unica mcp`
(лаунчер `~/.local/bin/unica`, подмена — `UNICA_LAUNCHER`) с `cwd` корня
проекта. Юника отвечает только `structuredContent`; клиент MCP DSH
проецирует его в текст модели начиная с 0.2.2-rc.2 (фикс `mcp-client`,
ntin60775/deepseek-harness#1). Воркспейс Юники фиксируется при старте;
вызов инструмента `cwd` не переключает: для второй копии — своя сессия,
а не второй вызов. Привязку подаёт доставка через `ZCODE_PROJECT_DIR` —
это имя env-канала юники (хост ZCode), не ZCode-слой контура (снят в
Т10) и не зависимость от ZCode: DSH не входит в хосты юники, а из её
каналов привязки (per-call meta Codex, MCP roots, env) клиенту DSH
доступен только env. Имя канала — решение оператора; нейтральный ключ
(`UNICA_PROJECT_DIR`) — кандидат в апстрим-ишью.

- `UNICA_RUNTIME_CACHE_DIR` указывает на глобальный кэш; проект своего
  кэша не держит.
- Handshake — протокол `2025-11-25`, `serverInfo` версии из `unica.yaml`,
  11 инструментов: `view`, `apply`, `resolve`, `search`, `check`, `diff`,
  `run`, `docs`, `task.get/result/cancel`. Юника обслуживает протоколы
  `2025-06-18`, `2025-11-25`, `2026-07-28`.
- Современный режим (`2026-07-28` через `server/discover` с `_meta`)
  отдаёт восемь инструментов: `task.*` доступны только сессиям прежних
  ревизий, вызов сам дожидается итога. `initialize` с предложением
  `2026-07-28` согласуется до `2025-11-25` — те же одиннадцать.
- `unica dap` — подкоманда ядра: DAP-адаптер по stdio, attach к серверу
  отладки платформы. В контур не подключена: отдельный юнит, спека
  `docs/plans/dap-debugging.md`.
- Соседние записи доставки: `1c-testpilot`, `1c-db` (с инстансами
  мультистенда), `1c-kd`.
- Пресет требует DSH с фиксом `mcp-client` (0.2.2-rc.2 и новее): на
  стоковом 0.2.2-rc.1 ответы Юники приходят в сессию пустыми.

## Поверхность Unica

- **Страницы.** `view`, `check`, `diff`, `docs`, `search` отдают длинные
  ответы страницами по `limit` (1–50) и `cursor`. Курсор и `page.stoppedBy`
  лежат на верхнем уровне ответа, не внутри `data`. Пока `cursor` непустой,
  ответ неполон. `view` принимает ещё `offset` и `from` (префикс без учёта
  регистра) — взаимоисключающие с `cursor`; страницы коллекций несут
  `data.offset` и `data.total`, на `.Props.*`/`.Can.*` эти аргументы —
  `bad_value`. `check {}` без `at` отдаёт вердикт workspace и группы
  диагностик страницами; `check {at}` — находки узла. На большом дереве
  `check` и `run` уходят в async-задачу: результат — через `task.result`,
  принятие задачи не ответ.
- **Поиск.** Буквальный `search` без `role` идёт до последнего совпадения,
  первая страница несёт `data.totals` (точный объём). Роли — `symbol` и
  `semantic`; роли `lexical` нет. `symbol`/`semantic` могут остановиться
  после первого окна и пометить неполноту. Находка называет, что открыть.
  `symbol` и граф вызовов обслуживает bsl-analyzer. Первая постройка
  индекса на большой конфигурации занимает десятки минут: ответ
  `dependencyPending` / `buildingIndex` — retryable-ожидание, повторяй тот
  же запрос; после готовности выдача точная (`searchComplete: true`).
  `semantic` требует внешний эмбеддинг-сервис (`EMBEDDING_URL` + адаптер);
  без него роль отказывает `provider_unavailable`. Обратный граф (`Caller`)
  на большой конфигурации может отказать `provider_limit_exceeded` —
  бюджет обхода; прямой (`Callee`) читается страницами.
- **Пакетный `resolve`.** `resolve {paths: ["…:4", …]}` переводит много
  путей/строк в логические адреса одним вызовом; ошибка одного элемента
  не роняет остальные.
- **Длинное свойство.** `<узел>.Props.<имя>` читает свойство целиком,
  когда обычный `view` упирается в предел; `<узел>.Can.<op>` — контракт
  операции. Оба адреса принимают `limit`, как одиночный узел.
- **Адресация.** `.Compilation` не адресуется; срезы
  `Interface.Public`/`Library`/`Override` адресуемы; адресуемы виды
  `Variable` и `Binding`, модули хранилищ настроек, обработчики
  HTTP-методов, SOAP-операций, подписок на события и регламентных
  заданий. `EventSubscription.Handler` принимает
  `<set>:CommonModule.<модуль>.<метод>`; короткая форма тоже принимается.
- **Операции `apply`.** `panels.set`, `homePage.set`, `attribute.copy`,
  `dimension.set`, `property.rename`, `props.set` на корне конфигурации и
  форме; `form.set` на корне конфигурации, члены метаданных правятся по
  адресу. Состав для узла — из `can`; применимость операции — по маршруту.
- **Правка свойств и связей.** `attribute.copy` отвергает неоднозначный
  источник; `relation.add/remove/replace` — только у видов с поддержанными
  связями; `attribute.set.values.toolTip` — только у реквизита табличной
  части справочника. Правятся `Name` корня конфигурации и его
  локализованные свойства; `SequenceFilling` (`AutoFill`/`AutoFillOff`) —
  у документа, `FillFromFillingValue` — у стандартного `Owner` справочника.
- **Запись кода.** `code.insert` без селектора дописывает в хвост;
  `code.replace` на адресе модуля требует `selector.anchor` (точное
  уникальное вхождение) и непустой `text`. Замена тела целиком — адрес
  `Body` узла модуля без селектора; `view` этого узла отдаёт `rev` —
  sha256 полного текста модуля, `code.replace` принимает необязательный
  `ifRev` той же формы. Расхождение — `conflict` с исходом `fixCall`,
  `next` ведёт к `ops[i].args.ifRev`: запись по устаревшему чтению
  отклоняется. Тело передавать без ведущего BOM.
- **Локализованные значения.** Локализованное значение — одна строка
  `НСтр` (`ru = '…'; en = '…'`) и на чтение, и на запись: `synonym`,
  `toolTip`, `Explanation`, заголовки форм (`title`, `inputHint`, Label
  `title.text`), заголовки СКД, локализованные свойства корня
  конфигурации. Плейн-строка на запись — отказ `bad_value` с `fixCall`;
  карта языков и массив `[{language, content}]` не принимаются. Набор
  языков заменяется целиком, пустая строка очищает. `view main:Configuration`
  отдаёт `synonym` этой строкой.
- **Формат выгрузки и поддержка.** Выгрузка старее минимально записываемого
  формата — `apply` отказывает `invalid_source` (`fixSource`); лечение —
  `source.reexport` набора (ниже). Конфигурация на поддержке поставщика
  закрыта от структурных правок: операции в `can` несут
  `blocked: configurationReadOnly`; правка живёт в расширениях.
- **Словарь операций.** Поле `implemented` убрано; недоступной операции в
  словаре нет. Контракт вызова — `argsSchema` из `unica.run {}`; при
  `support.state: limited` допустимо только `support.supportedArgs`.
  Состав словаря: `push` (включая `delete:<имя>` — удаление расширения
  с данными, вопрос человеку), `pull`, `infobase.create/restore/dump`,
  `source.reexport`, `make`, `download`, `launch`, `extensions.list/set`.
- **Переэкспорт набора.** `unica.run {op: source.reexport, args:
  {sourceSet, format}}` полностью переэкспортирует набор в записываемый
  формат через временную файловую базу: 2.20 пишет 8.3.27, 2.21 — 8.5.1,
  2.22 — 8.5.4; линия должна быть установлена. Проектная база не
  трогается, файлы набора заменяются. `source.reexport` и полный `pull`
  возвращают `warnings` об исчезнувших настройках выбора (`ChoiceList`,
  `ChoiceParameterLinks`, до 20 примеров): молчаливой потери нет.
- **`unica.docs`.** Источники — `platform-help` и `development-standard`;
  `configuration-documentation` отвечает `unsupported_source` (#939).
  `query` принимает `documentId`, выданный инструментом; адрес справки
  несёт сборку платформы; блок «See also» — структурные строки.
  Встроенная справка конфигурации до подключения источника читается
  напрямую: страницы `Ext/Help/<локаль>.html` у корня набора, объекта,
  формы и подсистемы описывают прикладную методологию, не платформу.
  Длинная страница — страницами, ответ может прийти задачей
  (`status: working`): ждать `task.result`, принятие задачи не ответ.
  Статья справки и комментарий метода отдаются полями.
- **Секреты и EOL.** Секрет подключения не попадает в сохранённые задания;
  правки XML не портят переводы строк в нетронутом тексте.
- **Вопросы человеку.** Часть операций спрашивает человека: подтверждение
  (перезапись базы `push force`, удаление расширения, замена данных DT,
  пересоздание файловой базы) и выбор (расхождение базы и набора, снятие
  с поддержки, запись в базу другой копии, смена поставщика). Канал —
  elicitation клиента; клиент без него (DSH) подтверждения исполняет как
  прежде, а выбор остаётся отказом с вопросом (`unica.choice` в
  structuredContent): решение выносится оператору, повтор вызова вслепую
  запрещён. Аргументы `humanConfirmation`/`humanReexport` ставит только
  сервер; вызов модели с ними отказывается.
- **Замок правок на время операции.** Исполняемые `pull`, `push`, `make`
  исключают правки исходников до завершения: параллельный `unica.apply`
  получает отказ.
- **Готовность перед правкой.** `pre-ready-check` сверяет рабочее
  пространство перед записью: замок рабочих копий базы, каталог сборки
  другой копии, незавершённая сборка — отказ с причиной.

## v8project и v8-runner

Полный справочник полей и регламент переезда —
`skills/1c-project-layout/references/v8project.md`. Коротко:

- `infobases` живут только в `v8project.local.yaml`: раннер отвергает
  карту в основном файле. Поддерживается только `origin`; несколько
  именованных баз, верхнеуровневый `connection`, смесь `infobase` +
  `infobases` отвергаются. `infobase` — прежнее имя `infobases.origin`,
  принимается один цикл в local-слое.
- Проекция конфига упразднена: раннер читает конфиг самой копии.
  Оставшаяся от прежних версий `.build/unica/runner-project/` удаляется
  при ближайшей операции записи; неудача удаления — предупреждение
  `former_runner_config_copy_kept`.
- `builder`, `basePath`, `execution_timeout`, `push.partialLoadThreshold`
  отвергаются. Полная загрузка — `push full: true`.
- `build` — прежнее имя `push`; принимается один цикл.
- Исполнители `providers`: `designer`, `agent`, `ibcmd`, `ibcmd-rs`,
  `webinst`; прежние имена `build`/`dump`/`init`/`load`/
  `infobase.configuration.export` переименовываются в
  `push`/`pull`/`infobase.create`/`upload`/`download`.
- `upload`, `apply`, `reset` как операции `unica.run` недоступны (#1246).
  Загрузка `.cf`/`.cfe` — ibcmd, не раннер. `unica.apply` (MCP) — другое,
  он правит исходники. Сборка `.cfe` — два пути: `unica make` (из
  исходников, расширение должно стоять в ИБ) и `ibcmd config save
  --extension=<имя>` (из базы) — скилл `1c-ibcmd-delivery`. Успех apply не
  равен донесённой версии: критерий — поколение расширения, не строка
  «успешно» и не `generation-id` основной конфигурации.
- Файловая база принадлежит рабочей копии. Запись из второй копии раннер
  предупреждает (`infobase_of_another_copy`), юника спрашивает человека
  (`infobase.another_copy`: продолжить или своя база); клиент без
  elicitation исполняет с предупреждением, как прежде. Каждой копии —
  своя база (`infobase.create`); владелец и проекция — скилл
  `1c-unica-worktree`.
- Память раннера о базе живёт в `localPath` (`.local`): хеши наборов,
  копия файла версий, журнал поколений. После обновления раннера память
  копии пуста — первый `push` без `force` отказывает `untracked_base`
  (называет набор); у кластерной базы отказ советует обычный `pull`, а не
  `--force`. Память заводит разовый `push force: true` (перезапись
  базы, вопрос человеку) или `pull`; `workPath` можно удалить — память
  переживает.
- Отказ среды и база другой копии приходят полями раннера; отмена
  вызова раннера — прерыванием, ответ раннера вместо убийства процесса;
  уборка копии начинается с `agent stop`.
- Живой агент Конфигуратора — умолчание раннера (`tools.designer_agent.
  live: true`): переживает команду, держит сеанс базы и лицензию; чужой
  исполнитель на занятой базе получает `infobase_busy` (выход —
  `agent release`/`agent stop`). Замок ИБ контура агента не снимает.
- Стык `ibsrv` ↔ `ibcmd`: локальный `ibsrv`, обслуживающий ту же
  файловую базу (`--db-path`/`--database-path`), даёт `infobase_busy` до
  запуска `ibcmd`, включая вложенные шаги, независимо от исполнителя —
  проверка стоит в общей точке `IbcmdDsl::run_with`. Текст несёт PID,
  сервер не гасится; чужой пользователь и невидимый список процессов
  проверку не останавливают. Узнаётся только эта форма запуска: `ibsrv`
  публикации (`--data`/`--config` из `publish_ib.sh`) под неё не попадает,
  и отказ приходит от самого `ibcmd` (exit 255, `provider_unavailable`).
- `ibcmd` без объявленного `user` у базы с пользователями отвечает
  `environment_unavailable` с `error.layer: infobase_user`, а не висит.
- Вывод процессов платформы ограничен 56 МиБ + 8 МиБ; усечение помечает
  `[v8-runner: N bytes of output omitted]`.
- Интерактивный `launch thin|thick|ordinary` без `--wait-for-exit` не
  передаёт `/DisableStartupDialogs`: окна лицензии и входа остаются
  человеку; `designer`, `mcp`, `--wait-for-exit` и тест — прежний ключ.
- Управляемые стенды раннера: `dbms`/`cluster` — Windows и Linux, `web`
  (`infobase.web.managed`, `tools.apache.path`; `apachectl` не
  принимается), `standalone` — только Windows. На Linux `start`/`publish`
  от root отказывают, `dbms` требует локаль `ru_RU.utf8`. Контур стенды
  раннера не использует: на Linux стенды поднимают свои скрипты
  (`start_1c_db.sh`, `publish_ib.sh`); `publish` раннера (webinst) в
  словарь `unica.run` не входит.
- CLI раннера вне словаря: `sessions`, `web`, `debug-server`,
  `launch --debug` в `unica.run` не входят. Умолчание
  `clone --source-dir` — `src/cf`; контур `clone` не использует.
- Форматы наборов 2.21/2.22 и линии платформы 8.5.1/8.5.4 поддерживаются:
  запись, новые файлы, заимствования, режимы совместимости и `props.set`/
  `form.set` — по линии набора.

## Известные границы

- **Публикации нет.** `unica.run` не публикует базу; `panels.set` и
  `homePage.set` — интерфейс, не веб-публикация. Контур закрывает это
  скиллом `1c-ibsrv-publish` через `publish_ib.sh`.
- **Дети HTTP-сервиса** (шаблоны URL, методы) не выражаются контрактом
  `object.create` целиком; апстрим — #529. Дети и права дописываются XML
  по разовой эскалации.
- **Размер вызова.** Ресурсные лимиты сведены в реестр (#1312), отказ по
  размеру результата называет размер и предел.
- **`push` формы с ручным динсписком** падает `ConfigFilesError`
  (unica#1877); доставка — ibcmd, скилл `1c-ibcmd-delivery`.
- **Большие деревья.** Отказы по размеру ответа сняты страницами и
  снимками на диске; зонтик #1119 (нагрузка больших конфигураций) открыт,
  admission-порог большого репозитория проверять живьём.
- **`extensions.list`/`pull`** — открытые #1797/#1798; серверной базе для
  IBCMD нужен `infobases.origin.dbms` (диагностика — #1103). Подсистемы
  основной конфигурации на файловой базе смотреть `execute_code` через 1c-db.
- **Запись тела с BOM даёт двойной BOM.** `code.replace`/`code.insert`
  дописывают свой BOM поверх уже стоящего в теле: файл получает
  `EF BB BF ×2`, модуль перестаёт компилироваться, любой вызов в такой
  модуль вешает канал до отстрела по таймауту. `unica.check` при
  несобранных диагностиках может отчитаться зелёным — компиляцию
  доказывать живой загрузкой. Лечение: повторный `unica.apply` с телом без
  ведущего BOM. На 0.16 явление не проверено.
- **Выбор без elicitation.** Клиент DSH не объявляет elicitation:
  вопросы-выборы ядра остаются отказом с вариантом ответа. Это
  граница канала, не дефект установки: решение принимает оператор,
  обходные аргументы подтверждения модель не передаёт.
- **Окна `launch`.** Интерактивный `launch` без `--wait-for-exit` не
  передаёт `/DisableStartupDialogs`: окна лицензии и входа остаются
  человеку; `--wait-for-exit` — прежний ключ.
- **Стык `ibsrv` ↔ `ibcmd`.** Локальный `ibsrv` на той же файловой базе
  останавливает `ibcmd` отказом `infobase_busy` до запуска; отказ не
  зависит от исполнителя и не снимается чужим пользователем или
  невидимым списком процессов.

## Траблшутинг

**Сервер не стартует.** `unica --help` отвечает не версией из `unica.yaml`
— смотреть лаунчер и `runtimes/unica`: пустой каталог означает, что
артефакт не докачан; прогрев — `unica-bootstrap prefetch --plugin-root
<каталог установки>` с `UNICA_RUNTIME_CACHE_DIR` контурного кэша.
`.partial` в `runtimes` — след оборванной закачки. Лаунчер на rc после
обновления — снести каталоги прежних версий (`--prune`).

**Сервер жив, первый вызов провайдера — `provider_unavailable`.**
Разошлись артефакты, не handshake: скилл `1c-unica-artifacts`, `/1c-doctor`
назовёт недостающий артефакт и версию.

**Handshake без хоста:**

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' | unica mcp
```

Ожидание — `serverInfo` версии из `unica.yaml` и 11 инструментов.
Современный режим `2026-07-28` (`server/discover` с `_meta`) отдаёт восемь
инструментов, `task.*` в нём нет, вызов сам дожидается итога; `initialize`
с этой же версией согласуется до `2025-11-25` и отдаёт одиннадцать.
Ожидание контура — всегда `2025-11-25`.

## Работа в git-ворктри

Воркспейс фиксируется при старте MCP: `cwd` сервера — корень проекта,
`cwd` вызова его не переключает. Второй копии — своя сессия и своя база;
владелец файловой базы и проекция конфига — скилл `1c-unica-worktree`.
Гейты контура — host-плагин `dsh-1c-contour`, отдельной разводки в проекте
нет.
