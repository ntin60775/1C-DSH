## Находки

### P1-1 · доказательства / демо-путь · п.6 «Готово» (spec:37)

**Утверждение.** Демо-путь п.6 недоказуем в своей последней части: `--proxy-only`
поднимает прокси *без клиента 1С* (`spec:100-102`), а все тулы прокси
исполняются через очередь команд клиенту — без клиента вызов висит, а не
отвечает; критерий сам себе противоречит `Ограничениям` той же спеки.

**Доказательство.**
- `spec:37`: «погашенный прокси → сессия без тулов → `--proxy-only` → тулы
  появились, **вызов отвечает**».
- `spec:78-80`: «`/health` ≠ «стенд готов»: без клиента 1С вызовы висят до
  `toolCallTimeoutMs` 60 с».
- `spec:100-102`: «`--proxy-only` выходит до клиента, Xvfb и stand-замка».
- Тулкит: локально (мимо очереди) отвечает только служебный хелп и только в
  режиме `server_host` с зарегистрированным потребителем —
  `onec_mcp_toolkit_proxy/mcp_handler.py:380`:
  `server_help = owner is not None and owner.mode == 'server_host' and tool ==
  'get_bsl_syntax_help'`; полный список тулов (`tools.py:1192-1881`:
  `execute_query`, `execute_code`, `get_metadata`, `get_event_log`, …) идёт в
  `consumer_registry` (`consumer_registry.py:11`).
- `.scratch/issue-16/03-stand.md:47`: «`POST /api/execute_query` без клиента —
  висит: command timeout 180 с в логе»; `.scratch/issue-16/05-proof.md:54`:
  «тулы есть; вызовы висят до 60 с».
- Подтверждает и issue #16: без клиента работает `initialize`/`tools/list`, но
  не вызовы.

**Что править.** Разбить п.6 на два шага с явной предусловием: (а)
`--proxy-only` → тулы `mcp__1c-db__*` появились (повтор `tools/list`, окно
ожидания ≥30 с — потолок backoff); (б) *после* полного подъёма с клиентом 1С
(канал поллит) → вызов отвечает. Либо назвать в п.6 предусловие «клиент 1С
поллит» и убрать `--proxy-only` из шага вызова. Текущая формулировка даёт
красную приёмку при исправном фиксе.

### P2-2 · покрытие · Цель vs п.6 (spec:23-26, spec:37)

**Утверждение.** Цель говорит про два носителя — прокси `:6003` **и** станцию КД
`:8060`, а приёмочная проба п.6 проверяет только `1c-db`; поведения `1c-kd` при
позднем подъёме нет ни в одном критерии «Готово» — только в спайке `.scratch/`,
который по правилам репо не коммитится.

**Доказательство.** `spec:23-26`: «погашенном прокси `:6003` или станции КД
`:8060`, получает **их** тулы». `spec:37` — единственный поведенческий критерий,
и он про прокси (`--proxy-only`). Политика на строке `1c-kd` (spec:32) в тесте
охраняет только форму конфига, не поведение. Доказательство поведения `1c-kd` —
`.scratch/issue-16/05-proof.md:31-42` (опыт A), а `.scratch/` эфемерно
(`AGENTS.md`: «`.scratch/` … производные или эфемерные — никогда не
коммитятся»).

**Что править.** Добавить в п.6 шаг для станции КД (станция погашена → сессия →
`start_kd_rules.sh` → тулы `mcp__1c-kd__*`) либо явно вынести поведение `1c-kd`
из Цели в отдельный пункт/тикет с названным носителем и не давать канону
`1c-kd-rules` (п.5) обещания без приёмки.

### P3-2 · доказательства / честность · бюджет (spec:47-49, spec:69-70)

**Утверждение.** «≈57 мин» — это только сумма задержек backoff; бюджет попытки
`startupTimeoutMs: 15_000` не учтён, поэтому обещанная граница занижена: при
отказе «чёрной дырой» (TCP не отвечает, а не RST) реальное исчерпание ≈88 мин.

**Доказательство.** `src/delivery/config.ts:334-335`: HTTP-строки
`1c-db`/`1c-kd` несут `startupTimeoutMs: 15_000`; бюджет per-attempt —
`packages/mcp/mcp-client/src/connection.ts` (в `.scratch/issue-16/01-mcp-client.md`
§«Бюджет реконнекта»: «+15 с на попытку (худший) … 5266.5 с = 87:47»). На
localhost отказ мгновенный, поэтому 57:31 верно — но формулировка «После бюджета
(~57 мин) тулы снимаются» (`spec:69`) подаёт нижнюю границу как точное число.
Живым замером не проверено.

**Что править.** В `Ограничения` записать «≈57 мин при мгновенном отказе
(localhost), до ≈88 мин при чёрной дыре TCP» — цифра нужна оператору, чтобы
понимать, когда ждать, а когда рестартовать.
