# Т3 «Ядровые гейты: doc, mcp, style, module»

Оценка: 3–5 дней (параллельно). Блокеры: Т2.

## Зачем

Четыре гейта несут обещание контура: мутации только после сверки с
документацией, прод-контур fail-closed, стиль BSL по паку, правила
модулей. Они независимы друг от друга и от Т4 — это основной батч
параллельных агентов. Спека:
[docs/plans/dsh-contour.md](../../docs/plans/dsh-contour.md).

## Что делается

- `doc_gate`: состояние «сверка пройдена», сброс на мутации, распознавание
  структурных операций.
- `mcp_gate`: fail-closed на testpilot/1c-db, признак `contour:` /
  `.dsh/1c`, распознавание REST через bash.
- `bsl_style_gate`: чекер пака по изменённым `.bsl`, advisory-отчёт.
- `bsl_module_gate`: правила структуры модулей, отчёт.
- Каждый гейт — на общем контракте Т2, со своим паритет-набором; агенты не
  правят общий контракт без согласования (диff по контракту — только с
  обоснованием в тикете).
- Паритет-векторы четырёх гейтов сохраняются в `tests/vectors/*.json`
  (вход, решение, класс причины) — регрессия переживёт удаление эталона.

## Демо-путь

На живом проекте: мутация без сверки — deny; прод-вызов `1c-db` — deny;
правка `.bsl` даёт отчёт стиля и модульных правил.

## Критерии приёмки (падают на базовом коммите)

- Паритет-тесты четырёх гейтов зелёные на корпусе эталона.
- Живая сессия: четыре поведения наблюдаются — deny ×2, отчёт ×2.
- Векторы четырёх гейтов лежат в `tests/vectors/`.
- Общий контракт не изменён без записи в тикете.

## Прогон (09.11)

Четыре гейта переписаны на TS на общем контракте Т2: `doc`, `mcp`,
`bsl-style`, `bsl-module`. Состояние, которое эталон держал файлами на
сессию (`doc-gate/<sid>.json`, `style-bridge/<sid>.json`,
`module-bridge/<sid>.json`), живёт в памяти сессии — оно умирает вместе с
ней, как и файловое.

### Изменения общего контракта (с обоснованием)

1. `ExecutedCall.resultText` — гейту сверки нужен ответ docs-провайдера:
   признака ошибки мало, `doc_gate` решает по содержимому ответа.
2. `PostDecision.notice` — advisory-отчёты стиля и носителя. Эталон отдавал
   их через `additionalContext` в stdout; в хосте это
   `additionalContexts` у решения после вызова.
3. `GateState.memory` — память сессии для гейтов с состоянием (флаг сверки,
   планы правок). Файлы состояния эталона на сессию снимаются.
4. `GateState.standLockStatus` — гард stand-замка `mcp_gate`: нужен живой
   замок по строке подключения.
5. `GateState.styleChecker` (`StyleCheckerPort`) — чекер стиля вынесен в
   порт: гейт не запускает процессы, адаптер выбирает движок
   (`1C_STYLE_ENGINE` → `bsl-style-engine` в PATH → скрипт пака).
6. `LockRecord.kind`/`pid` — поля записи stand-замка.

### Доказательства

- Паритет: 35 сценариев в четырёх корпусах (`tests/vectors/doc.json`,
  `mcp.json`, `bsl-style.json`, `bsl-module.json`). Сценарий — шаги
  `pre`/`post` по порядку: гейты с состоянием нельзя проверить одним
  вызовом. Эталон проигрывает тот же сценарий процессами хука со своим
  файловым состоянием, TS — чистыми функциями с памятью сессии; сверяются
  решение, класс причины и названные файлы. Стиль проверяется на одном
  движке: заглушка `tests/helpers/fake-style-engine.py` подставляется обеим
  реализациям через `1C_STYLE_ENGINE`.
- Юнит-тесты: приоритет `.dsh` над legacy `.zcode` (признак контура,
  allowlist, файл эскалаций носителя), override `mcp_gate.dangerous`,
  серверный профиль `profiles.yaml`, разборы носителя (директивы,
  `Перем`, права `value=true`), осмысленность ответа сверки, порт чекера
  (движок из env, фрагмент, отсутствие движка).
- Всего в наборе 169 проверок (35 паритетных сценариев T3, 16 юнит-тестов
  T3, остальное — Т2).

### Пробелы

- **Живая проверка упирается в поколение модуля.** Профиль держал
  загруженный модуль Т2; подмена пакета и переключатель строки дают
  `ERR_REQUIRE_CYCLE_MODULE` — хост грузит свежее поколение только при
  перезапуске. После merge и перезапуска хоста плагин поднимет Т3.
  Проверка четырёх живых поведений остаётся за оператором либо за
  следующим запуском.
- **Отчёт стиля и носителя живьём** требует успешной записи в `.bsl`
  исходника, а её открывает только сверка (`doc_gate`), то есть вызов
  `unica.docs` — MCP ставится в Т5. До Т5 эти два отчёта живьём не
  наблюдаются, только паритетом и юнит-тестами.
- `apply_patch` без `file_path` в `doc_gate` не проверяется (как у
  эталона): путь берётся из `file_path`/`path`, текст патча не разбирается.
  Пробел унаследованный, записан на Т6/Т7.
