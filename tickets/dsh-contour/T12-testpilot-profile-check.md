# Т12 «Профили testpilot: сверка `base` в doctor и bootstrap»

Оценка: ~60 мин. Блокеров нет. Хвост после живой приёмки Т10 юнита #56
(находка 16.11, решение оператора — отдельный тикет).

## Зачем

Живая приёмка Т10 на `erp-demo` упала на первом же GUI-соло:
`launch_client: no such infobase directory — …/.dsh/1c/testpilot/../../build/ib`.
После переезда раскладки на `.dsh/1c` профиль остался с двухуровневым
`base`: относительный путь резолвится от каталога файла и уходит в
`.dsh/build/ib`. Шаблон `templates/profiles.example.yaml` уже несёт
`../../../build/ib`; тот же двухуровневый `base` — ещё в двух проектах парка
(`dealer-network-orders`, `project-bp`).

Грабли невидимы до первого GUI-прогона: `1c-project-bootstrap` создаёт
`profiles.yaml` только когда файла нет (существующий не перечитывает), а
`doctor.py` в разделе `mcp` проверяет только наличие файла. Правка в
`erp-demo` сделана на месте (файл вне git), парк не проверен.

## Что делается

- `scripts/doctor.py`, `check_testpilot`: для найденного `profiles.yaml`
  сверить `base` каждого профиля — относительный путь резолвится от каталога
  файла (канон шаблона), каталог обязан существовать. Битый base — FAIL
  `mcp.testpilot-base` с именем профиля, сырым и резолвнутым путём.
  Серверная база (`server: true`, `base` вида `Кластер\База`) и профиль без
  `base` не проверяются. Разбор — stdlib (doctor не тянет PyYAML): формат
  профилей простой — `profiles:` → имя → `base`/`server`.
- `skills/1c-project-bootstrap/SKILL.md`, шаг 2: профиль существует — не
  перезаписывать, но сверить `base` по тому же правилу и назвать битый;
  профиля нет — создать по шаблону, как сейчас.
- `tests/test_doctor.py`: фикстуры «битый base», «правильный base»,
  «серверный/без base»; в `--json` — код проверки и резолв.

## Демо-путь

`python3 scripts/doctor.py dealer-network-orders` (или `project-bp`) на
текущем дереве — FAIL с путём `.dsh/build/ib`; `… erp-demo` — OK;
`… zupupr` (серверный `v56\…`) — без новых FAIL. Текст bootstrap на
существующем профиле называет битый base и файл не трогает.

## Критерии приёмки (падают на базовом коммите)

1. Артефакт: тест — профиль `base: ../../build/ib` в `.dsh/1c/testpilot/`
   даёт FAIL `mcp.testpilot-base`, резолв оканчивается `.dsh/build/ib`;
   `base: ../../../build/ib` — ok. На базовом дереве обе фикстуры зелёные
   (ложно) — падает.
2. Артефакт: тест — `server: true`/`v56\база` и профиль без `base` не дают
   FAIL. Ожидание: инвариант — зелёный до и после.
3. Артефакт: живой прогон doctor на `project-bp` — FAIL с путём; на
   `erp-demo` — ok; на `zupupr` — без новых FAIL. Ожидание: проверка ловит
   реальный парк, а не только фикстуру.
4. Артефакт: текст шага 2 bootstrap — существующий профиль сверяется по
   base и не перезаписывается; профиля нет — создаётся по шаблону. Проверка:
   грепы раздела и `python3 scripts/lint_skill_frontmatter.py` — зелёные.

## Границы

- Проекты не правятся: doctor и bootstrap называют битый base, а перезапись
  профиля — решение оператора (вне тикета).
- Пароль не проверяется: живой базы у doctor нет, `password` остаётся
  значением файла вне git.
- Схема профилей 1c-testpilot не меняется, `password_env` не вводится.
