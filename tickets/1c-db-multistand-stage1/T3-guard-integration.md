# Т3 «Гард: интеграция замка»

Оценка: ~50 мин. Блокеры: Т2.

## Зачем

Замок без потребителей — мёртвый код; старты клиентов должны брать его сами.

## Что делается

- `scripts/start_1c_db.sh`: перед подъёмом клиента — взять stand-замок на
  строку подключения; отказ exit 2 «база занята» с pid владельца; при
  остановке стенда (stop-ветка, путь kill_client) — выпустить.
- `hooks/mcp_gate.py`: запуск клиента тест-клиентом — `tc_session` с
  `action="launch_client"` (реальная поверхность testpilot 1.9.x; имя
  `mcp__1c-testpilot__launch_client` из исходной формулировки у сервера
  не существует — поправлено оператором 05.11) блокируется на замкнутой
  базе — гейт читает статус stand-замка по
  connection профиля (attach и stop второй клиент не поднимают — не
  блокируются).

## Демо-путь

Два старта одной файловой базы: первый поднимается и держит замок, второй
выходит 2 с «база занята (pid …)»; после остановки первого второй старт
проходит.

## Критерии приёмки (падают на базовом коммите)

1. Артефакт: тест в `tests/test_start_1c_db.py` — второй старт при живом
   владельце замка. Ожидание: exit 2, в тексте pid владельца. На базовом
   дереве замок не берётся — тест падает.
2. Артефакт: тест в `tests/test_mcp_gate.py` — инструмент
   `mcp__1c-testpilot__launch_client` при активном stand-замке на базе
   профиля. Ожидание: exit 2. На базовом дереве stand-замков нет — тест
   падает.
3. Артефакт: тест выпуска замка при остановке стенда. Ожидание: после stop
   взятие проходит. На базовом дереве падает.

## Границы

Подчистка мёртвых владельцев — механика Т2; автоматическая копия базы для
тест-клиента не делается (отклонено дельтой) — максимум подсказка в
fail-сообщении.

## Расхождения (разбор прогона)

- Имя инструмента: спека и тикет называли `mcp__1c-testpilot__launch_client`
  — такого инструмента у testpilot 1.9.2 нет (tools/list: tc_app…tc_session).
  Реальная форма — `tc_session` с `action="launch_client"`; гард стоит на
  ней (проверено живым venv, `_runtime.py`). Формулировка спеки и тикета
  поправлена оператором 05.11.
- Демо-путь «второй выходит 2» — в окне подъёма первого. При полностью
  поднятом стенде второй старт выходит 0 («уже отвечает») до взятия
  замка — идемпотентный старт сохранён, лишний клиент при этом не
  поднимается. Предусловие зафиксировать в живой приёмке Т8.
- Тест-клиент замок НЕ берёт — гейт только читает (pid клиента хуку
  PreToolUse недоступен). Обратное направление открыто: после тест-клиента
  start_1c_db видит свободный замок и может поднять второй клиент.
  Граница — за оператором (сузить спеку или решение по взятию замка).
- pidfile может указывать на shim-обёртку (podman/distrobox) — замок на
  обёртку умрёт раньше клиента, гард молча слепнет. Обычная установка
  держит pid (setsid делает exec). Граница названа; полное закрытие
  (pid реального клиента) — Т6/Т7.
- release при живом владельце замок не снимает (kill не всегда
  доставляется — правило среды) — --stop предупреждает.
- Серверные базы не замкиваются ни скриптом, ни гейтом (гард файловой
  базы, зеркало с двух сторон).
- Шаблон templates/profiles.example.yaml даёт base `../../../build/ib` —
  при копировании как есть гард слепнет (ключ уводится выше корня).
  Правка шаблона — этап 5, к Т3 не относится.
- Резолв связи в stand_lock_py дублирует резолв CONN скрипта; на Т5
  (db-instances) разойдётся — замок ставится на main, пока стенд живёт
  на инстансе. Носитель резолва — Т5.
