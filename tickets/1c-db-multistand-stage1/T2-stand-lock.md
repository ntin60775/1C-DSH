# Т2 «Stand-замок: механика»

Оценка: ~45 мин. Блокеры: нет.

## Зачем

Соло-правило файловой базы (второй клиент на ту же базу виснет на файловых
блокировках) держится дисциплиной агента; нужен механический замок.

## Что делается

`hooks/ib_lock.py`: второй вид замка `stand:<нормализованная строка
подключения>` — без TTL, владелец — pid, живость проверяется свежей pgrep,
мёртвый владелец освобождает замок (взятие подчищает stale). API:
взять / выпустить / статус. Существующие код-замки unica не меняются —
разные пространства ключей.

## Демо-путь

Прогон `tests/test_ib_lock.py`: цикл жизни — взял → второй взявший получил
отказ → владелец убит → свежая проба процесса пуста → замок свободен,
взятие проходит. Краснота на базовом коммите a2a963c: новые тесты против
базовых хуков (`git archive a2a963c hooks` в пустой каталог + новые
`tests/test_ib_lock.py` и `tests/_lib.py`) — ровно 2 FAIL через
hasattr-гард, остальной набор продолжает работать; golden-проверка ключа
код-замка на базе зелёная (инвариант, не доказательство).

## Расхождения (разбор прогона)

- «свежая pgrep» из формулировки → проба `/proc/<pid>/stat`: pgrep этого
  procps не умеет выборку по pid («неверный ключ — „p“»), ps -p верит
  зомби; смысл сохранён — свежая проба таблицы процессов владельца при
  взятии и в статусе. Формулировка спеки («Готово» 4) — правка только
  решением оператора.
- Взятие атомарное (жёсткая ссылка готового файла вместо
  чтение→запись): ревью-панель воспроизвела обе-ок при одновременном
  старте. Остаточная гонка «двое разом увидели мёртвого владельца»
  осталась — арбитр flock вынесен в решение Т3/Т6 (flock порта из Т6
  её не закрывает — нарочно проверено панелью).
- Usr=/Pwd= вырезаны из ключа и записи замка: иначе смена пароля
  создавала бы второй стенд, а пароль жил бы в файле состояния.
- Не вошло (за оператором/Т3): идентичность владельца — голый pid без
  времени старта (переиспользованный pid держит фантомный замок до
  ручного сноса файла); stand-locks не выметаются автоматически; тихая
  деградация гарда при непишущемся каталоге состояния (политика
  код-замка); контракт pid для Т3 — живущий всю работу с базой процесс,
  не shim-обёртка.

## Критерии приёмки (падают на базовом коммите)

1. Артефакт: тест цикла жизни stand-замка. Ожидание: второй take блокирован;
   после смерти владельца take проходит. На базовом дереве вида `stand:` нет —
   тест падает.
2. Артефакт: тест «код-замок и stand-замок на одной базе не блокируют друг
   друга». Ожидание: работают независимо. На базовом дереве вида `stand:` нет.
3. Артефакт: регресс ключа код-замка по нормализованной строке подключения.
   Ожидание: прежнее поведение (инвариант).

## Границы

Интеграция замка в старты — Т3; TTL stand-замку не добавляется; чистка stale
— только через pgrep-живость владельца при взятии.
