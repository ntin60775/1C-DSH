# Skill: deliver
# Поставка и обновление OntoShip в проекте

Полный протокол поставки и обновления OntoShip в один проект живёт
здесь; носители интента деплоя — оркестраторы (`ontoship-deploy`,
`1c-contour-deploy`) и прямая команда оператора в сессии продюсера.
Блок входа init только называет команду. deliver — весь акт
поставки/обновления; init — точка входа, его запускает deliver после
установки. Скоуп — только ядро OntoShip: паки стандартов, team-бандл
и стек deliver не ставит и не обновляет — это их контуры.

## Когда использовать

- Прямая команда оператора в сессии продюсера: поставить OntoShip
  в проект, обновить установку, «деплой и обновление [имя_проекта]».
- Оркестратор деплоя передал протокол исполнителю на один проект.
- Интент деплоя парка из произвольной сессии несут оркестраторы;
  здесь — протокол одного проекта. Имя проекта X бери из запроса,
  не угадывай.

## Протокол

1. **Источник.** deliver исполняется там, где чекаут ядра доступен:
   `scripts/install.sh` лежит в корне репо ядра, не в бандле.
   Link-продюсер резолвит путь ядра из realpath бандла
   `.agents/skills/deliver`; copy-продюсер — ask оператора о чекауте
   ядра. Молчаливого клона и remote нет — правило одного пути. Канал
   продюсера и путь использованного install.sh фиксируй в доказательствах.
2. **Поиск X.** имя → реестр потребителей и соседние чекауты; не найден
   — ask пути, не угадывай.
3. **Состояние.** `install.sh --check <X>` до обновления определяет
   состояние. Warning установщика (legacy-записи, выведенные бандлы)
   называй в отчёте до утверждения «поставлено»; `check: ok` не отменяет
   warning.
4. **Канал.** Свежая установка — ask канала link/copy; обновление —
   тем же каналом; смена канала — ask оператора, молча канал не
   меняется. Замена неверного симлинка в `.agents/skills/` — штатное
   действие установщика (relink), не деструктив.
5. **Установка/обновление.** install.sh соответствующего канала.
   Drifted-копия — отказ установщика «copy differs» называется,
   протокол останавливается на ask удаления: деструктив у потребителя
   — только с подтверждения оператора. Legacy-симлинки на продюсера
   установщик сносит сам при установке (`removed legacy`); реальные
   legacy-копии бандлов сносит сам с архивом
   (`~/.dsh/state/ontoship/legacy-archive`, `removed legacy copy`);
   миграция знаний из архива — решением оператора; выведенные бандлы
   не трогает — называй и спрашивай.
6. **Init.** После свежей установки и при обновлении — скилл init:
   идемпотентен, блок входа — только между маркерами ontoship, текст
   вне маркеров не трогается. install.sh сам init не запускает.
7. **Акт rollout.** Коннектор — бандл реестра `consumer-registry` в
   чекауте ядра (шаг 1): `.agents/skills/consumer-registry/` рядом с
   `scripts/install.sh`. Каталог сессии роли не играет: бандл живёт на
   стороне продюсера, его отсутствие в каталоге — не отсутствие
   коннектора. Прочитай `SKILL.md` бандла и следуй правилам; валидатор и
   шаблоны — рядом в бандле. Файла реестра нет — исполни старт ведения
   по правилам бандла (machine/project заполняются фактами), затем пиши
   акт. Бандла нет в чекауте ядра или он нечитаем — запись не делается,
   пробел называется в финальном отчёте; фолбэк-записи в другой носитель
   нет. Реестр ведёт продюсер: deliver не ставит реестр потребителям и не
   требует его наличия. Факт rollout пишется только в реестр; continue.md
   целевого проекта deliver не пишет.
8. **Отчёт фактами.** Версия до/после, канал, вывод check, warning,
   акт или названный пробел — финальным сообщением сессии.

## Контракт акта

- `action` = `rollout` (свежая поставка) | `update` (обновление).
- `actor` = сессия deliver.
- `to`/`version` потребителя = тег link-дерева, иначе `git describe`
  (dev+sha); для copy — версия фактически поставленного снимка: тег или
  `git describe` чекаута ядра, с которого снята копия (факт байтов);
  чекаут не резолвится — `unknown` с названным пробелом (прежнюю
  запись не переносить: она врёт о содержимом).
- `from` = прежнее `consumers[].version`; прежней записи нет — `from`
  опускается, версия baseline называется в note потребителя.
- `updated_at` обновляется.
- Перед поставкой сверь открытые followups (`done: false`) по правилам
  скилла реестра; после свежей поставки и после обновления пиши followup
  «свежая сессия потребителя».
- `acceptance[]` не ведётся: акт несёт поставку и прогон поставщика
  (`result: ok` — именно это, не приёмка потребителя); проверка на
  стороне потребителя живёт followup-ом свежей сессии.
- deployed.json не заводится.

## Границы

- Ask-ноги протокола (поиск X, удаление drifted-копии, смена канала,
  чекаут для copy-продюсера) исполняются только с ответом оператора;
  ответа нет — протокол стоит, нога называется пробелом.
- Отсутствие бандла реестра в чекауте ядра и отсутствие файла реестра —
  разные ветки: бандла нет или он нечитаем — пробел; файл отсутствует при
  доступном бандле — старт ведения, затем акт.
