# Init

Настрой точку входа проекта OntoShip. Запускай это один раз на проект, после
установки ядра. Скилл **идемпотентен**: повторный запуск ничего не меняет, и
`git diff` после него пуст.

**Чем владеет init.** Четыре файла, ничего больше:

- `AGENTS.md` — управляемый блок между `<!-- BEGIN ontoship -->` и
  `<!-- END ontoship -->`. Всё вне маркеров — текст проекта: никогда не правь, не
  перемещай и не переписывай файл целиком. Исключение — одна пустая
  строка-разделитель перед блоком при его вставке: она отделяет блок от текста
  проекта и при следующих запусках не переписывается.
- `.gitignore` — строки, которые требует харнесс: `.gitmark/`, `*-map.html`,
  `.scratch/`, `.agents/skills/`, `.agents/packs/` — строка навыкового корня
  скрывает project-local установку скиллов, строка корня паков — установленные
  паки стандартов.
- `.agents/config.toml` — реестр ролей: одна секция `[agents.<роль>]` на роль
  с обязательным ключом `model`.
- `docs/ops/continue.md` — скелет состояния работы: init создаёт его, только
  когда файла нет; существующий файл init не открывает и не правит.

Init пишет эти четыре файла и ничего больше: он не создаёт индекс команд или
генерируемые таблицы, не пишет ничего в `docs/`, кроме скелета
`docs/ops/continue.md` при отсутствии файла, не пишет навыковые корни каналов,
`.gitmark/` или любой другой файл и не запускает `index`, `lint` или `map`.
Если он не может записать один из четырёх файлов, он сообщает об этом и
останавливается — он никогда не подменяет расположение.

**Новые файлы — байт-в-байт по шаблону, включая завершающий перевод
строки.** Новый `AGENTS.md` (блок), `.gitignore` (пять строк) и скелет
`docs/ops/continue.md` кончаются переводом строки по шаблону. Правило
«не добавляй завершающий перевод строки, которого в файле не было»
относится только к существующим файлам.

## 0. Проверь харнесс

Харнесс — DSH, он определяется доступным инструментом хоста: в сессии есть
`list_subagent_models` и `subagent`. Нет — назови пробел и остановись:
веток у init больше нет, и на чужом харнессе он не работает.

## 1. Найди корень проекта

Запусти `git rev-parse --show-toplevel` из корня проекта; откатись к текущему
каталогу, когда проект не git-репозиторий. Пиши все четыре файла в этом корне.

`AGENTS.md` читается из корня проекта; харнесс может также смотреть родительские
каталоги и собственные глобальные файлы, но точка входа принадлежит корню проекта.
Не пиши глобальный `AGENTS.md` или вложенный `AGENTS.md`.

## 2. Обнови AGENTS.md

Прочитай файл **не нормализуя его байты** — бинарный ввод-вывод или текстовый с
`newline=''`. Определи стиль переводов строк по первой строке (`\r\n` или `\n`) и
используй его для вставленных строк. Маркер присутствует, только когда целая строка,
без учёта завершающего `\r`, равна строке маркера. Затем примени ровно один из пяти
случаев:

| случай | действие |
|---|---|
| `AGENTS.md` отсутствует | создай его, содержащим ровно блок ниже |
| файл существует, ни одна строка маркера не встречается | добавь одну пустую строку, затем блок; каждая существующая строка остаётся |
| один BEGIN и один END, в этом порядке, и внутренний текст равен шаблону | ничего не меняй; файл уже актуален |
| один BEGIN и один END, в этом порядке, и внутренний текст отличается | замени только внутренний текст, сохрани строки маркеров и всё вне них; сообщи `[WARN]` |
| любая строка маркера встречается, но пара — не ровно один BEGIN, затем один END | ничего не меняй, сообщи `[FAIL]`, остановись — остальные файлы не трогай |

Последний случай покрывает одиночный маркер, перевёрнутую пару, дублирующую пару и
маркер, который стоит не на своей строке. Отказывай закрыто: догадка о том, какая
пара — «та самая», рискует уничтожить текст проекта.

**Блок.** Дословный шаблон; не переформатируй, не переименовывай, не добавляй
и не удаляй строки.

````markdown
<!-- BEGIN ontoship -->
## База знаний (OntoShip)

- Точка входа: [`docs/README.md`](docs/README.md) — главный индекс KB; у каждой папки
  есть индекс `README.md`.
- Ищи до ответа или записи: загрузи скилл `kb-search`. Движок лежит в
  `.agents/skills/kb-search/gitmark.py`; корень — `.agents/skills`.
- Новые или обновлённые документы: загрузи скилл `kb-curate` — сначала поиск, никогда
  не дублируй.
- Сопровождение после правки документов:

  ```sh
  python3 .agents/skills/kb-search/gitmark.py index
  python3 .agents/skills/kb-search/gitmark.py lint --strict
  python3 .agents/skills/kb-search/gitmark.py map -o docs-map.html
  ```

- KB — это markdown + git: `.gitmark/`, `*-map.html` и `.scratch/` производные или
  эфемерные — никогда не коммитятся.

## Вход в работу (OntoShip)

- Изменения этого проекта идут через ship-флоу: скилл `ship` исполняет
  один тикет за запуск — вручную командой `/ship`; свободные правки
  в обход тикета не делаются — прямые решения оператора выше этого
  правила.
- Запрос плана открывает draft-спеку через скилл `grilling`; режим плана
  харнесса не используется.
- Состояние и порядок работы — [docs/ops/continue.md](docs/ops/continue.md):
  сессия продолжается оттуда и берёт следующий тикет оттуда же.
- Команды: «стартуй юнит» — открыть draft-спеку; `ship` — командой
  `/ship` или «исполняй тикет N»; «деплой и обновление [имя_проекта]» —
  скилл `deliver`.
<!-- END ontoship -->
````

Блок — генерируемое содержимое. Инструкции конкретного проекта принадлежат вне
маркеров. Копия бандла вне проекта (исходный checkout) корнем не считается:
корень установки — `.agents/skills` проекта, куда смотрит движок в блоке.
Правка внутри блока теряется при следующем init; скажи об этом, когда блок
заменяется.

Сравнивай внутренний текст после нормализации переводов строк (`\r\n` → `\n`) с обеих
сторон, чтобы файл с CRLF и в остальном актуальным блоком не переписывался. При
записи сохраняй каждый байт вне блока как был; не добавляй завершающий перевод
строки, которого в файле не было.

## 3. Обнови .gitignore

Создай файл, если его нет. Иначе добавь только строки, которых ещё нет как
строки (сравнивай обрезанную строку). Оставь каждую существующую строку, её
порядок и комментарии — никогда не удаляй дубль, более широкий шаблон или
комментарий. Добавляй отсутствующие строки в этом порядке:

```text
.gitmark/
*-map.html
.scratch/
.agents/skills/
.agents/packs/
```

Если файл непустой и не заканчивается переводом строки, добавь его перед
добавлением. Заверши переводом строки после последней добавленной строки.
Если все строки набора уже есть, ничего не меняй.

## 4. Создай скелет continue.md

`docs/ops/continue.md` — состояние работы проекта: сессия продолжается от
этого файла. Файла нет — создай каталог `docs/ops` и запиши в него файл
`continue.md`: тело ниже дословно, единственная подстановка — сегодняшняя
дата в формате YYYY-MM-DD вместо `<дата>` в поле `updated`; отчёт называет
`created`.

Файл существует — не правь его ни байта: отчёт называет `unchanged`, и init
переходит к следующему шагу. Содержимое существующего файла принадлежит
проекту: расхождение с шаблоном — не дефект, последующие запуски init его
не читают и не меняют.

```markdown
---
node_type: runbook
title: Продолжение работы над проектом
service: _platform
status: active
updated: <дата>
---

# Продолжение работы над проектом

Это канонический старт каждой сессии. Источник истины — этот файл и тикеты,
не память сессии.

## Состояние

Где проект: закрытые юниты и тикеты, открытый юнит, последний merge.

## Открытая работа

Что исполняется: юнит, тикет, на чём остановились, что дальше.

## Порядок тикетов

Юниты и тикеты в порядке исполнения; блокировки отмечены.

## Что осталось

Отложенная работа: пункт с условием возврата.

## Стартовый промпт

Текст, с которого открывается сессия. Чек-лист фазовых переходов:
вычитка спеки перед план-гейтом — скилл `grilling`; проекционная
валидация после план-гейта, до нарезки — скилл `critic`; самопроверка
после приёмки нарезки — скилл `to-tickets`; ревью-панель перед merge —
скилл `ship`.
```

## 5. Бутстрап ролей

`<корень>/.agents/config.toml` — реестр ролей: одна секция `[agents.<роль>]`
на роль, обязательный ключ `model`.

**Роли команды.** Роли команды — архитектор, оркестратор, исполнитель и
сборщик контекста — поставляет DSH-бандл пресетов уровня профиля, не пак
стандартов; init бандл не устанавливает и ролей команды в реестр не
пишет. Установку сверь перечнем бандлов профиля (`plugin_manager`):
бандл есть — назови его в отчёте ссылкой на установленный бандл профиля
(пакет и версия), без имени личного репозитория и без литералов
маршрутов; бандла нет — шаг молчит; инструмента нет — назови пробел
в отчёте.

**Конфиг существует.** Сверь роли ядра — `reviewer-spec`, `reviewer-tests`,
`reviewer-code`, `reviewer-kb`, `critic`, `curator` — с секциями конфига и
приведи их к матрице: механики поставки и проекта одни, `model` и `level`
ролей ядра и пул `[validation]` равны матрице (`roles.py`: `ROLE_ROUTES`,
`POOL_ROUTES`). Прогони `python3 skills/init/sync_config.py
.agents/config.toml` из корня проекта: скрипт правит только эти секции,
печатает изменения (`role: route set to …`, `validation: pool set to …`),
незнакомые секции, ключи, комментарии и порядок оставляет байт-в-байт;
`--check` красный, когда реестр разошёлся. Изменения назови в отчёте,
повторный прогон печатает «already matches» — идемпотентность. Секции ролей
паков и прочее вне матрицы — знание проекта: см. «Паки стандартов» ниже.

**Конфига нет — бутстрап.**

1. Источник моделей — `list_subagent_models`: без аргументов — провайдеры, с
   провайдером — модели, с провайдером и моделью — уровни. Маршрут роли —
   строка `<provider>/<model>`. Пустой список — назови пробел и остановись:
   имена моделей не угадываются.
2. **Стандартная раскладка.** Роли ядра поставляются одной раскладкой:

   | роль | `model` | `level` |
   |---|---|---|
   | `reviewer-spec`, `reviewer-tests`, `reviewer-code`, `reviewer-kb` | `qwen-token-plan-max/qwen4-max` | `medium` |
   | `critic` | `qwen-token-plan-max/qwen4-max` | `xhigh` |
   | `curator` | `qwen-token-plan/qwen3.8-flash` | `medium` |

   Сверь её с живым каталогом: все шесть маршрутов и их уровни доступны —
   запиши её без ask. Хоть один маршрут или уровень недоступен — спроси
   оператора: в вариантах только активные пары, ближайшая к стандарту
   первой; назови отклонение от стандарта в отчёте.

   **Паритет с реестром проекта.** Таблица выше — матрица поставки, и она
   обязана совпадать с реестром ролей проекта (`.agents/config.toml`,
   секции `[agents.<роль>]` ролей ядра: `model` и `level`). Меняешь матрицу
   в реестре — меняешь таблицу тем же коммитом; расхождение — красно́
   (`tests/test_role_registry.py`), не «значение проекта». Значения пула
   валидации — наоборот, значение проекта: в таблицу их не выносить.

   **Пул валидации.** Секция `[validation]` — часть матрицы: три различных
   модели по model-части, пары — в `roles.py` (`POOL_ROUTES`) и в таблице
   выше. На бутстрапе сверь пары с живым `list_subagent_models`; смерти
   маршрута — ask оператора с активными вариантами, ближайшая к матрице
   первой; отклонение назови в отчёте. Пул — источник маршрутов членов
   консилиума, причина выбора — в отчёте гейта.
3. Отсутствие ключа `level` — штатный дефолт модели; у ролей матрицы `level`
   пишется всегда, дефолт касается ролей паков.
4. Сгенерированные определения ролей не нужны: DSH читает реестр в момент
   запуска.

**Паки стандартов.** Каталог `.agents/packs/` проекта несёт паки
стандартов команды и стека (контракт — бандл `pack`). Каталога нет —
паков нет, шаг молчит. Каталог существует — проверь каждый пак
валидатором бандла `pack` (`validate_pack.py` рядом с его SKILL.md):
невалидный манифест — назови пропуск в отчёте, роли такого пака не
регистрируй. Роли валидных паков (`reviewer-<kontur>-<aspect>`)
дополняют реестр:

- **Конфиг существует.** Правило идемпотентности — то же, что в
  бутстрапе ядра выше. Роль пака без секции — останови шаг: назови роль,
  причину и варианты модели из живого `list_subagent_models`; секцию пиши
  только после ответа оператора, в делегированном прогоне ask поднимает
  оркестратор; молча не дописывай.
- **Конфига нет — бутстрап.** Роли ядра пишутся стандартной раскладкой
  (выше); модели ролей паков стандартная раскладка не назначает —
  спроси оператора бутстрап-вопросом: варианты из живого
  `list_subagent_models`, ближайшая к раскладке ядра первой; отказ
  источника моделей — по правилу бутстрапа ядра.

Приоритет норм: канон > стандарты проекта > пак команды > пак стека >
базовый документ; неразрешимый конфликт — вопрос оператору.

## 6. Проверь

Из корня проекта:

```sh
git diff -- AGENTS.md .gitignore .agents/config.toml docs/ops/continue.md
git status --short
```

Первый прогон: `git status --short` называет созданные (`??`) и изменённые
(`M`) файлы; diff показывает блок, отсутствующие строки, новый конфиг и новый
скелет — для новых файлов diff пуст, пока файл не в индексе или коммите.
Второй прогон: **никаких изменений** — ни нового diff, ни новых строк в
`git status --short`. Это и есть проверка идемпотентности, а не утверждение.
Если второй прогон что-то меняет, текст блока, сравнение строк, запись
конфига или запись скелета нестабильны: исправь скилл, не замазывай.

Проверь, что пара маркеров ровно одна:

```sh
grep -c '^<!-- BEGIN ontoship -->$' AGENTS.md   # 1
grep -c '^<!-- END ontoship -->$' AGENTS.md     # 1
```

## 7. Отчёт

Назови каждый файл и что произошло: `created`, `appended` (назови строки),
`updated inside markers` или `unchanged`. Для `docs/ops/continue.md` итог —
`created` или `unchanged`; содержимое существующего файла в отчёт не входит.
При обновлении предупреди, что правки внутри блока не выживают. При `[FAIL]`
процитируй проблему маркеров и заяви, что ничего не изменено. Для конфига
назови итог: записанные роли и их модели, пул валидации, либо пропуски ролей
ядра и секции пула, либо пробел источника моделей. Для паков назови итог:
валидные паки и их роли, пропуски манифестов и незарегистрированные роли
паков. Для ролей команды назови team-бандл ссылкой на установленный бандл
профиля (пакет и версия) — без имени личного репозитория и литералов
маршрутов; бандла нет — шаг молчит. Генератор не запускается и перезапуск
хоста не нужен.

Затем передай дальше: следующий шаг — построить KB. `docs/README.md` — главный индекс;
новые документы идут через `kb-curate`; команды сопровождения — в блоке. Не запускай
их в рамках init.
